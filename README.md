# mesh-app-2001

## Technical Blueprint

## 📡 Лёгковесный распределённый **Event‑Bus** на WebSockets с поддержкой **pub/sub‑топиков**  
**Код‑имя проекта:** `ws-event-bus`  

> **Цель** – предоставить ultra‑low‑latency, масштабируемый и безопасный брокер сообщений, который может работать в кластере из десятков узлов, обслуживая как браузерные, так и серверные клиенты через обычный WebSocket‑соединения.  

Ниже собран **консенсус** из предложений, аудита и security‑ревью: полный технический дизайн, список рисков и их смягчения, а также готовый набор артефактов для CI/CD и деплоя.

## 1️⃣ Функциональные требования

| № | Требование | Краткое описание |
|---|------------|------------------|
| **F‑1** | **Подключение** | Клиенты открывают обычный WebSocket (`ws://` или `wss://`). |
| **F‑2** | **Pub/Sub** | `PUBLISH <topic> <payload>` → доставляется всем подписанным клиентам. |
| **F‑3** | **Иерархические топики** | Поддержка `sport/football`, wildcard‑подписок `sport/#`, `sport/+/score`. |
| **F‑4** | **QoS‑0 (fire‑and‑forget)** | По умолчанию – без подтверждения доставки (минимальная задержка). |
| **F‑5** | **QoS‑1 (ack‑based)** | При запросе `qos:1` брокер ждёт `ACK` от каждого получателя, пере‑отправляет при таймауте. |
| **F‑6** | **Авторизация** | JWT‑токен в `Sec-WebSocket-Protocol` или в первом `CONNECT`‑сообщении. |
| **F‑7** | **ACL** | Права `publish/subscribe` привязываются к ролям/группам в JWT‑claims. |
| **F‑8** | **Горизонтальное масштабирование** | Добавление новых брокеров без простоя. |
| **F‑9** | **Fail‑over** | При падении узла клиент автоматически переподключается к другому брокеру, подписки восстанавливаются. |
| **F‑10** | **Observability** | Метрики, трассировка, логирование. |
| **F‑11** | **DevOps‑готовность** | Docker, Helm, GitHub Actions. |

## 3️⃣ Архитектурный обзор

### 3.1. Схема компонентов

```
+-------------------+          +-------------------+          +-------------------+
|   Client A (WS)   | <------> |   Broker Node 1   | <------> |   Broker Node N   |
+-------------------+          +-------------------+          +-------------------+
          ^                               ^                               ^
          |                               |                               |
          |                               |                               |
          |                               |                               |
          |                               |                               |
          |                               |                               |
+-------------------+          +-------------------+          +-------------------+
|   Load‑Balancer   | <------> |   Service‑Disc    | <------> |   Raft‑Consensus   |
+-------------------+          +-------------------+          +-------------------+

Legend:
 • Load‑Balancer – L4/L7 (Envoy, HAProxy, NGINX) с sticky‑session + consistent‑hash.
 • Service‑Disc – Kubernetes DNS / Consul / etcd (для обнаружения брокеров).
 • Raft‑Consensus – лёгкий Raft‑модуль (node‑raft) хранит метаданные кластера:
   – лидер, список узлов, версия топика, ACL‑политики.
```

### 3.2. Ключевые паттерны

| Паттерн | Зачем | Как реализовано |
|--------|-------|-----------------|
| **Raft‑based leader election** | Предотвращает split‑brain, гарантирует единую точку согласования подписок/ACL | `node-raft` хранит `cluster_state` в памяти + периодический snapshot в `etcd` (для восстановления). |
| **Consistent hashing + virtual nodes** | Равномерное распределение нагрузки, минимальные перемещения при масштабировании | Хеш‑функция `xxhash64(topic)` → брокер‑ответственный за хранение подписок данного топика. |
| **Sticky‑session (IP‑hash) на LB** | При переподключении клиент попадает к тому же узлу, где уже есть подписки в памяти | Envoy `hash_policy: source_ip`. |
| **Optimistic subscription versioning** | Убирает race‑condition при одновременной подписке/отписке | Каждый список подписок хранит `version` (uint64). При изменении – атомарный `compare‑and‑swap`. |
| **Ack‑based QoS‑1** | Гарантирует доставку без дублирования | После `PUBLISH` брокер ждёт `ACK` от каждого получателя, хранит `msgId` в `inflight` map с TTL. |
| **Graceful shutdown + drain** | Позволяет безопасно выводить узел из кластера | При SIGTERM брокер объявляет себя `draining`, перенаправляет новые подписки, завершает `inflight` сообщения. |

## 4️⃣ Детали реализации

### 4.1. Технологический стек

| Layer | Tech | Почему |
|-------|------|--------|
| **Runtime** | **Node.js 20 (LTS)** + native `ws` | Низкий overhead, широкая экосистема, простота разработки. |
| **WebSocket** | `ws` (npm) | Высокопроизводительный, поддерживает TLS, ping/pong. |
| **Consensus** | `node-raft` (or `raft-js`) + `etcd` for snapshots | Малый размер, готовый к работе в K8s. |
| **Discovery** | **Kubernetes Service** + **CoreDNS** (fallback: Consul) | Автоматическое масштабирование. |
| **Load‑Balancing** | **Envoy** (L4+L7) – `hash_policy` + `consistent_hash` filter | Прозрачно распределяет соединения, поддерживает health‑checks. |
| **Metrics** | `prom-client` → `/metrics` | Prometheus‑scrape. |
| **Tracing** | `@opentelemetry/api` + `@opentelemetry/sdk-node` | OpenTelemetry collector. |
| **Logging** | `pino` (JSON) + `pino-http` | Структурированный, low‑overhead. |
| **
